# Корпус структурных регрессий критика, версия 1

Включённые 18 ситуаций полностью синтетические: 10 dev, 8 test. Каждая содержит
`synthetic: true`, `expert_confirmed: false`. Они проверяют код и обработку
известных ошибок, не представляют выборку реальных судебных дел. Разработчик видел
обе части; test здесь не является слепой финальной оценкой качества.

## Схема строки JSONL

- `situation_id`: уникальный ID ситуации.
- `split`: `dev` или `test`.
- `case_groups`: идентификаторы дел, по которым разделяются выборки. Не путать
  с ID акта. Для реальных данных вычислять `case_key` из нормализованного номера.
- `synthetic`, `expert_confirmed`: обязательные явные булевы признаки.
- `request`: только действующий `ReviewRequest` 2.0: `intake`, `coverage`,
  `comparisons`, `evidence`, при необходимости `contract_version`.
- `gold_labels`: `expected_verdict` и `expected_issues`.

`Evidence` требует `id`, `case_id`, `act_id`, `case_key`, `page`, `quote` и остальные
поля своего контракта. Legacy `case_id` равен `act_id`. В `Finding` обязательно
сохраняются `dimension`, `relation`, `text`, `evidence_ids`. Поля `statement_type`
в текущем контракте нет: добавлять его в корпус или выдачу соседнего агента нельзя.

Все акты, версии, связанные фабулы и производные одного реального дела должны
попадать в одну часть. Eval проверяет пересечение `case_groups` и ID актов на всём
корпусе до фильтрации split, уникальность ситуаций и принадлежность Evidence
заявленным группам. Правильность исходного группирования проверяет разметчик:
выдуманные разные ключи одного дела автоматическая проверка распознать не сможет.

## Как размечать

1. Отделять утверждения клиента, доводы сторон и выводы суда. `assertion_type`
   должен подтверждаться контекстом оригинала; наличие слов «суд установил» само
   по себе недостаточно для юридической классификации.
2. `text_verified` означает только дословное совпадение с полученным текстом.
   Этот флаг не подтверждает смысл, качество OCR или оригинальность PDF.
3. `history_complete: true` допустим только после проверки доступной цепочки
   и охвата источников. Отсутствие апелляции в переданных данных не доказывает
   неполноту и не доказывает окончательность: неизвестность обозначается false
   либо отсутствующим полем. Критик формулирует это как «не подтверждено».
4. Допустимые вердикты: `acceptable`, `revise`, `insufficient`. `ok` недопустим.
   `acceptable` этой реализации означает отсутствие обнаруженных структурных
   ошибок; `sufficient` всё равно false, юридическая проверка не выполнена.
5. Для каждого ожидаемого замечания указать `reason`, `target`, `evidence_ids`,
   `blocking`. Категории перечислены в `ISSUE_REASONS` критика. Сравниваются
   отдельные вхождения, адресат, ссылки и блокирующий признак; текст сообщения
   и сгенерированный хеш ID не являются меткой.
6. При `missing_reference` поле `evidence_ids` пустое: неизвестный ID нельзя
   передавать как существующее доказательство в ответе критика. Адресат comparison,
   исправление ссылки выполняет сопоставитель. Неразрешённое блокирующее замечание
   без валидных ссылок ограничивает весь отчёт по действующему контракту.
7. Сам факт ссылки на довод стороны допустим, например при сравнении возражений.
   Правило `party_as_court` срабатывает только при узкой явной формулировке
   в начале тезиса и отсутствии опор, помеченных иначе, чем party_argument.
   Это сигнал перепроверки, не универсальная детекция подмены атрибуции.

## Метрики и ограничения

Eval передаёт критику только `request`, без gold и split. Он считает micro
precision/recall обнаружения размеченных замечаний и точность вердиктов.
Совпадение причины при неправильном адресате или Evidence ID не засчитывается.
При нулевом знаменателе precision/recall имеют значение null, пустой split — ошибка.
`--check` возвращает ненулевой код при несовпадении любой метки.

```text
python scripts/eval_critic.py --split dev --check --out reports/critic-eval-dev.json
python scripts/eval_critic.py --split test --check --out reports/critic-eval-test.json
```

Для полного ТЗ участника 5 ещё нужны 30–50 реальных задач с экспертной разметкой,
непересекающаяся слепая test-часть, версии корпуса/модели/промптов, ошибки и пропуски,
сравнение поиска без критика и полной системы, время/токены и прогон с юристом.
Precision@5 и Recall@20 измеряются на размеченном пуле выдачи; наличие API-ключа
не является обязательным условием для офлайн-оценки сохранённой выдачи.
