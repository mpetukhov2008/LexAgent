# Передача корпуса участнику 5

Ответственный за ручную проверку — участник 5, согласно указанию владельца проекта.
Автоматические оценки не подтверждены человеком и не называются экспертными.

## Что подготовлено

- `eval/retrieval/tasks_v1.jsonl`: 40 гипотетических задач, ссылки на страницы и
  цитаты трёх исторических актов, черновые оценки всех дел пула.
- `eval/retrieval/review_template.json`: пустые оценки для заполнения; null
  не принимается как подтверждение. Поле note должно объяснять оценки.
- `eval/critic/corpus_v1.jsonl`: 18 отдельных синтетических регрессий структуры.
- `scripts/build_case_corpus.py`: загрузка реальных оригиналов и метаданных
  через настроенный Parser API, без публикации ключей и PDF в Git.
- `scripts/eval_retrieval.py`: case-level Precision@5, Recall@20, время поиска.
- `scripts/eval_pipeline_variants.py`: одинаковый замороженный пул для лексического
  варианта, модели без критика и полной системы; сохраняет время, токены, проверки
  и материалы для ручной оценки. По умолчанию один запрос, два платных модельных
  варианта. Для большего набора нужно явно передать --limit.

Это старт процедуры разметки, а не готовая экспертная выборка из 40 независимых
реальных дел. Внешние оригиналы старых ссылок не были подтверждены прямой загрузкой;
исторические тексты следует сверить. Нельзя публиковать юридическую точность
на основании filename отчёта или совпадения подстроки.

## Работа проверяющего

1. Загрузить оригиналы и цепочки по реальному доступу к источнику либо получить
   сохранённые оригиналы в data/originals. Для стартовых номеров:

   ```text
   python scripts/build_case_corpus.py --case А70-7129/2024 --case А41-31683/2026 --case А67-5348/2026 --limit 8
   ```

2. Для каждой задачи проверить исходную страницу, атрибуцию цитаты, права, объект,
   размещение, фиксацию, требования, стадию, последующие акты и отличия. Уточнить
   гипотетическую фабулу: она не выдаётся за реальную историю клиента.
3. Заполнить оценки **каждого** дела: 0 — неприменимо, 1 — частично применимо,
   2 — существенно применимо. Предварительное правило «дело-источник релевантно»
   не является правильной меткой по умолчанию; отрицательные оценки тоже проверить.
   В note указать основание, страницы и существенные ограничения.
4. Не делить производные одного дела между dev/test. Сейчас две группы дел находятся
   в dev и одна в test. Этого мало для статистических выводов: расширить число
   независимых дел и подготовить новые слепые тестовые задачи. Разработчик уже видел
   оба стартовых split; их нельзя назвать независимым финальным тестом.
5. При подтверждении указать настоящее имя проверяющего. Если предметная юридическая
   компетенция отсутствует, это предварительная разработческая разметка: нужна
   дополнительная проверка юристом до заявления юридического качества.

## Применение оценок и измерение

Сохранить заполненную копию review_template.json отдельным файлом и выполнить:

```text
python scripts/review_corpus.py --reviews path/to/reviews.json --reviewer "Имя проверяющего" --out data/corpus/reviewed-tasks.jsonl
python scripts/eval_retrieval.py --corpus data/corpus/reviewed-tasks.jsonl --split test --out reports/retrieval-expert.json
```

До ручной проверки использовать только явно предварительный режим:

```text
python scripts/eval_retrieval.py --allow-draft --split test --out reports/retrieval-draft.json
```

Три исполнения на одном пуле, при настроенной GigaChat:

```text
python scripts/eval_pipeline_variants.py --corpus data/corpus/reviewed-tasks.jsonl --limit 1 --out data/eval/variants.json
```

Для сохранённого нового пула актов eval_retrieval поддерживает --acts с JSON-массивом.
Все дела пула должны получить оценки для каждой оцениваемой задачи; нельзя считать
неразмеченные документы автоматически нерелевантными. После расширения пула обновить
labels, исходные ссылки и группы, зафиксировать версию, хеш корпуса и split.

Precision@5 использует знаменатель 5, даже если выдача короче. Recall@20 считается
относительно размеченного известного пула; при трёх делах он почти неинформативен.
Время и модельные токены сохраняются отдельно. Корректность смысла сравнений,
пропущенные отличия и полезность записки оцениваются вручную по материалам variants;
поисковые метрики не подменяют эту оценку.
