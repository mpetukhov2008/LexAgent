# Техническое задание для команды

Версия 0.3, 7 ноября 2026. Пять участников, шесть агентов.

## Продукт и результат к защите

Веб-сервис для поиска применимой арбитражной практики по спорам о копировании
фотографий, инфографики и текстов карточек товаров. Юрист описывает ситуацию,
уточняет обстоятельства и получает проверяемую подборку: почему дело подходит,
чем отличается, что сказал суд, какие доказательства важны и что ещё неизвестно.

К защите нужен сквозной работающий сценарий с реальными опубликованными актами,
интерфейсом, журналом агентов и измерениями качества. Количество агентов не заменяет
качество поиска. Балл сходства не называется вероятностью победы.

Граница первой версии: арбитражные споры о контенте карточек. Не обещаем охват всей
судебной системы и полноту всех опубликованных решений.

## Что уже есть

- Участник 1: полноценный инструментальный агент разбора, FastAPI, очередь,
  PostgreSQL, контрольные точки, история, уточнения, интерфейс.
- GigaChat-2-Pro подключена через `langchain-gigachat` и `langchain-core`.
  LangChain отвечает за модель и вызовы инструментов; оркестратор и хранение — код проекта.
- В `app/pipeline.py` работают базовые роли 2–6: их предстоит развить владельцам.
- В `app/sources.py` есть Parser API, ограничение запросов, кеш, проверка URL и PDF-текст.
- В `app/library.py` есть постоянная библиотека и простой лексический поиск.
- Автоматические тесты используют заглушки внешних API; отдельно есть живые прогоны GigaChat.

Parser API при проверке отклонил оба предоставленных ключа с кодом 40301.
Получение реальных актов через этот ключ пока не подтверждено. Это внешний блокер,
не доказательство отсутствия дел. До устранения можно импортировать реальные тексты
в библиотеку, явно отмечая пользовательское происхождение.

## Общие правила реализации

1. Каждый участник владеет минимум одним агентом: цель, инструкции, инструменты,
   выбор действий, схема результата, ограничения, журнал и проверки.
2. Модель не выполняет произвольный SQL, код, команды ОС или произвольные URL.
3. Сведения клиента, доводы стороны и установленные судом обстоятельства различаются.
4. Каждый судебный вывод должен ссылаться на конкретный акт, страницу и цитату.
5. Отсутствие данных, ошибка источника и отсутствие результатов — разные состояния.
6. Несколько актов одного дела не считаются независимыми аналогами.
7. Новые компоненты используют текущие Pydantic-контракты или согласованное
   расширение с версией; нельзя молча менять поля соседнего участника.
8. Ключи — только в локальном `.env`, шаблон — без значений. В PR и отчётах нет клиентских секретов.
9. Демо и заглушки явно помечены; итог защиты показывает происхождение каждого документа.
10. Для каждого PR: проблема, изменение, проверка, ограничения. Живые вызовы API
    запускаются отдельно и не входят в обычный CI.

Живой LangChain/GigaChat-Pro прогон: шесть сведений без лишних уточнений на полном
учебном примере. Это проверка одного сценария, не статистическая оценка качества.

### Что доделать в командной версии

1. Подключать полноценные реализации остальных участников вместо базовых фаз,
   сохраняя формат событий и обработку частичного результата.
2. Расширить миграции PostgreSQL для нормализованных таблиц Case, JudicialAct,

3. Добавить общий бюджет запуска: суммарные вызовы модели/источника, время,
   возможность отмены и управляемое продолжение отдельного этапа.
4. Добавить редактирование карточки с происхождением исправления; исходные сведения
   и старые версии сохранять, не превращать правку пользователя в судебный факт.
5. Улучшить разбор свободных фабул по набору участника 5: ненужные уточнения,
   смешанные даты, присоединение к карточке, неизвестный автор размещения.
6. Провести общую приёмку интерфейса и документации после интеграции команды.

### Приёмка

- Полная фабула не требует повторения уже явно указанных сведений на контрольных примерах.
- Неполная фабула приводит к конкретным вопросам, не догадкам.
- Повтор HTTP-запроса не создаёт дубль задания.
- Перезапуск worker сохраняет завершённые этапы; старый worker не может перезаписать результат.
- Отказ поиска не уничтожает успешно разобранную карточку.
- Сквозной браузерный тест: ввод → уточнение → поиск → цитата → экспорт → история.

**Вне обязательного объёма предварительной защиты:** публичный многопользовательский
доступ. Если он нужен, отдельно реализуются аутентификация, права, серверное TLS,
резервное копирование и ограниченный пользователь БД.

## Участник 2 — агент-исследователь и судебные источники

**Собственный агент:** №3, исследователь дела.
**Начальные файлы:** `app/sources.py`, `app/library.py`, исследовательская фаза `app/pipeline.py`.

### Задачи

1. Установить рабочий канал получения реальных актов. По Parser API выяснить
   у поставщика причину 40301 и доступность отдельно KAD и RAS. Не подменять
   отсутствие доступа молчаливой демонстрационной выдачей.
2. Реализовать адаптер источника с отдельными операциями поиска, получения карточки,
   списка актов и загрузки документа. Добавить пагинацию, ограничения, кеш и повтор
   временных ошибок; недействительный ключ не повторять бесконечно.
3. Сохранять оригинал PDF, хеш, URL, время получения, номер дела, суд, дату, инстанцию,
   тип акта, извлечённый текст по страницам и статус качества извлечения.
4. Добавить OCR для сканов. Текст после OCR явно маркировать; сохранять страницу
   оригинала для проверки. Не считать текст без ошибок только потому, что OCR завершился.
5. Связывать первую инстанцию, апелляцию, кассацию и последующие акты. Если цепочка
   неполная, возвращать неизвестный статус. Отмена или изменение должны быть заметны.
6. Сделать исследовательского агента, который выбирает содержательные акты,
   читает нужные страницы и фиксирует: требования, возражения, доказательства,
   установленные обстоятельства, мотивы и результат.
7. Подготовить согласованный стартовый набор реальных дел по фото/инфографике.

### Инструменты агента

`list_case_acts`, `read_act_page`, `get_case_history`, `record_evidence`, `finish_research`.
Доступ к произвольным URL не давать; использовать ID из реестра источников.

### Контракт результата

Карточка Case с идентификатором и номером; массив JudicialAct; связи актов;
Evidence с act_id, page, quote, типом утверждения и статусом проверки;
отдельные `history_complete`, `text_quality`, `warnings`.

### Приёмка

- Реальное дело открывается по источнику; реквизиты совпадают.
- Повторная загрузка одного PDF не создаёт дубли.
- На примерах с обжалованием показаны все доступные значимые акты и ограничения полноты.
- На скане явно видно использование OCR; ошибка извлечения не превращается в пустое решение.
- Проверены 403/429/тайм-аут, повреждённый PDF, документ без текста и небезопасный URL.

**Передать:** агент, адаптер, миграции/контракт, набор реальных актов, тесты, краткую инструкцию.

## Участник 3 — агент поиска и индекс

**Собственный агент:** №2, планировщик поиска.
**Начальные файлы:** поисковая фаза `app/pipeline.py`, `Library.search` в `app/library.py`.

### Задачи

1. Реализовать нормализацию запроса по объекту, способу размещения, доказательствам
   и требованиям. Не включать идентификаторы клиента без необходимости.
2. Построить полнотекстовый индекс PostgreSQL с русскоязычной обработкой и фильтрами.
3. Добавить смысловой индекс в pgvector. Модель embeddings выбирать по русским
   судебным текстам на контрольном наборе; учитывать её лицензию и требования к памяти.
4. Объединять лексическую и смысловую выдачу; не сравнивать напрямую несопоставимые
   численные шкалы. Хранить происхождение кандидата и поисковую формулировку.
5. Разбивать длинные акты на фрагменты с сохранением act_id и номера страницы.
6. Реализовать агентный цикл: поиск → оценка достаточности → уточнение формулировки
   или фильтров → дополнительный поиск → завершение в пределах бюджета.
7. Объединять результаты по делу, оставляя ссылки на релевантные акты и фрагменты.
8. Подключить фильтры суда, периода, объекта и процессуальной стадии к интерфейсу.

### Инструменты агента

`search_lexical`, `search_semantic`, `search_external`, `inspect_candidates`,
`refine_query`, `finish_search`.

### Контракт результата

Массив кандидатов с case_id, act_id, fragment_id, источником и баллом ранжирования;
журнал запросов и фильтров; размер/дата корпуса; ограничения охвата и причины остановки.
Балл поиска не должен называться вероятностью выиграть дело.

### Приёмка

- Есть сравнение «по словам» / «по смыслу» / «гибридный» на одном и том же наборе.
- Измерены Precision@5, Recall@20 относительно размеченного пула и время поиска.
- Результаты не дублируются по одному делу; изменённые фильтры действительно меняют выдачу.
- Пустая выдача приводит к ограниченному расширению поиска; недоступность источника видна.
- Отчёт содержит не только удачные примеры, но и пропуски подходящих дел.

**Передать:** агент, индексатор, поисковый модуль, миграции, результаты измерений и тесты.

## Участник 4 — сопоставитель, составитель отчёта и экран результатов

**Собственные агенты:** №4 и №6.
**Начальные файлы:** comparison/report в `app/pipeline.py`, `app/static/search.js`.

### Агент №4: задачи

1. Определить схему юридического сравнения: конкретный объект, права, авторство,
   способ размещения, участие продавца/площадки, фиксация нарушения, требования,
   возражения, стадия и значимые даты.
2. Сравнивать сведения клиента с установленными обстоятельствами, отдельно учитывая
   доводы сторон. Не приписывать суду любое предложение из судебного акта.
3. Запрашивать дополнительные страницы через исследовательский агент, когда
   короткого фрагмента недостаточно.
4. Для каждого аналога показывать совпадения, отличия, неизвестные обстоятельства
   и доказательства. При недостаточности текста понижать уверенность.
5. Отдельно выделять потенциально благоприятную и неблагоприятную практику,
   не подменяя эту оценку одним исходом «иск удовлетворён».

Инструменты: `inspect_case`, `read_evidence`, `request_research`, `record_comparison`, `finish`.

### Агент №6: задачи

1. Собирать отчёт только из прошедших проверку карточек и доказательств.
2. Ссылаться на Evidence ID для каждого существенного судебного утверждения.
3. Учитывать замечания критика; спорные выводы либо исправлять, либо явно помечать.
4. Формировать список недостающих доказательств и вопросов для юриста.
5. Не добавлять новые номера дел, нормы, цитаты или проценты вероятности.

Инструменты: `get_verified_materials`, `check_report_references`, `revise_report`, `finish_report`.

### Интерфейс

Карточки дел, сортировка применимости, сравнение рядом, переход к странице оригинала,
видимые причины исключения, благоприятные/неблагоприятные примеры, замечания критика,
источники каждого вывода, печать и удобный экспорт.

### Приёмка

- Список ссылок отчёта является подмножеством реально полученных доказательств.
- Нет уверенной применимости без проверенной опоры на источник.
- Существенное различие видно рядом с совпадением, а не спрятано в конце отчёта.
- На мобильном экране читаются источники и ограничения, нет горизонтального переполнения.
- Браузерный тест проверяет переход от вывода к цитате и оригиналу.

**Передать:** два отдельных агента, схемы Comparison/Report, экран результатов,
тесты, примеры с полезными и неприменимыми аналогами.

## Участник 5 — агент-критик, оценка качества и приёмка

**Собственный агент:** №5.
**Начальные файлы:** critique и verify_evidence в `app/pipeline.py`, `tests/`, `reports/`.

### Задачи агента

1. Проверять связь вывода с цитатой, различать наличие текста и его смысл.
2. Искать неправильную атрибуцию: довод истца назван выводом суда, промежуточный
   акт назван окончательным, другая фактическая ситуация названа аналогом.
3. Запрашивать противоположную практику и значимые отличия через агента поиска.
4. Возвращать задачу на поиск или исследование не более согласованного числа раз.
5. Выдавать structured verdict: допустимо, нужна доработка или недостаточно данных,
   с Evidence ID, объяснением и адресатом замечания.

Инструменты: `verify_quote`, `inspect_comparison`, `request_counterexamples`,
`request_revision`, `finish_review`.

### Оценка качества

1. Совместно с юристом собрать 30–50 задач: фото, инфографика, права не доказаны,
   общая карточка, автозаполнение площадкой, недостаточная фиксация, разные инстанции.
2. Для каждой задачи разметить применимые/неприменимые дела и основания разметки.
3. Разделить разработку и финальный тест; разные акты одного дела не должны утекать
   между частями набора. Зафиксировать версии корпуса, промптов и модели.
4. Измерять Precision@5, Recall@20 на известном пуле, подтверждённость цитат,
   долю выводов без опоры, пропущенные отличия, время и расход токенов на запуск.
5. Сравнить простую поисковую базу, поиск без критика и полную систему.
6. Отдельно тестировать команды внутри документов, выдуманные цитаты,
   отсутствующие последующие акты, ошибку источника и противоречия во вводе.
7. Провести пользовательский прогон с юристом и записать, где интерфейс заставляет
   перепроверять слишком много или скрывает важные ограничения.

### Приёмка

- Есть воспроизводимый отчёт с размером выборки, метриками и конкретными ошибками.
- Цели качества согласованы после базового замера; целевые значения не выдаются за достигнутые.
- Критик обнаруживает специально внесённые ложные цитаты и неправильные ссылки.
- Его решение влияет на последующий поиск/отчёт и видно в журнале.
- Нельзя объявить систему проверенной только на синтетических happy-path примерах.

**Передать:** агента-критика, размеченный набор, инструкцию разметки,
eval-скрипт, отчёт сравнения вариантов и сценарий общей приёмки.

## Порядок интеграции

1. Участники 1 и 2 согласуют Case/JudicialAct/Evidence и получение первой партии актов.
2. Участник 5 начинает разметку этой партии; участник 3 строит базовый индекс.
3. Участник 4 подключает сравнение по полученным Evidence ID.
4. Участники 3 и 5 добавляют ограниченный цикл поиска контрпримеров.
5. Участник 4 собирает проверяемый отчёт, участник 1 интегрирует UI и восстановление.
6. Команда фиксирует модель, корпус и конфигурацию; участник 5 проводит финальную оценку.

Первая контрольная точка — небольшой реальный набор дел с проверенными текстами,
а не большое число красиво сгенерированных отчётов. Сроки назначаются после
подтверждения источника и даты защиты.
