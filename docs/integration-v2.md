# Контракт интеграции 2.0

Владелец общей интеграции — участник 1. Исследователь — участник 2, критик —
участник 5. Общие модели находятся в app/contracts.py. Новые реализации
размещаются в отдельных модулях; переписывать app/pipeline.py не требуется.

## Идентификаторы

В старом API cases — список актов, а evidence.case_id указывает на ID акта.
Это значение сохраняется для совместимости. Новые данные дополнительно имеют
act_id и case_key. case_key — устойчивый идентификатор дела по номеру.
Нельзя молча заменить старый case_id на ID сгруппированного дела.

CaseRecord объединяет act_ids; JudicialAct содержит страницы и источник.
Evidence содержит id, act_id, legacy case_id, case_key, page, quote,
assertion_type и text_verified. Наличие текста не доказывает истинность или
правильную атрибуцию: court_finding выставляет исследователь после анализа,
а не валидатор подстроки. Слова клиента по-прежнему хранятся в intake.fields.

## Участнику 2

Реализовать объект с асинхронным методом
research(request: ResearchRequest) -> ResearchResponse.
request.acts — полученные акты со страницами, request.intake — карточка клиента.
Ответ — evidence, warnings, history_complete. Для дополнительных материалов
использовать собственный адаптер источника; соблюдать общий бюджет оркестратора.
Нужно возвращать фактически прочитанные тексты. На границе pipeline цитаты снова
проверяются по доступным страницам; если нужны новые акты, сначала согласовать
расширение ResearchResponse. ID доказательства нормализует сервер.

## Участнику 5

Реализовать объект с асинхронным методом
review(request: ReviewRequest) -> ReviewResult.
Вход: intake, comparisons, evidence, coverage. Выход: verdict
(acceptable/revise/insufficient), issues, concerns, sufficient.
В issue указываются id, target (search/research/comparison/report), message,
evidence_ids и blocking. Ссылка может указывать только на существующее Evidence.
Недостаточность истории/корпуса нельзя устранить декларацией sufficient=true.

## Порядок включения

Сначала тесты контракта на синтетических данных, затем передача объекта
через параметры research_agent и critic_agent конструктора SearchPipeline.
Без них сохраняется существующая базовая реализация. Для подключения без изменения
оркестратора участник 2 предоставляет app/agents/research.py с классом
CaseResearchAgent(settings), участник 5 — app/agents/critic.py с классом
CriticAgent(settings). app/integrations.py загружает только эти доверенные модули.
Также можно передать готовые объекты в create_app(settings=..., research_agent=...,
critic_agent=...) или SearchPipeline.

Для verdict=revise предусмотрен один цикл исправления сравнений с повторным
review. Неразрешённые blocking-замечания закрывают соответствующие доказательства
для отчёта. Замечания к search/research сохраняются как revision_requests и видны
в предупреждениях; автоматическое исправление сравнения их не закрывает.
Внешние агенты обязаны соблюдать бюджет и таймаут; прямые внутренние вызовы их
собственных провайдеров не учитываются обёрткой основных ролей автоматически.

Сетевые проверки —
отдельно с настроенными ключами. Участники работают в своих ветках, не меняют
общие схемы молча и не сливают изменения в main без общей проверки.
