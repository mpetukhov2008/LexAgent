# Разбор перед импортом в LexAgent — 9 ноября 2026

## Вывод

Это содержательная основа локального исследовательского MVP. Есть сервер, очередь,
хранение, интерфейс, агент разбора и базовая последовательность пяти следующих ролей.
Полноценная система качественного поиска юридических аналогов пока не закончена.
Главный незакрытый вопрос — применимость найденной практики, а не наличие интерфейса
или подключения к модели. Процент готовности без согласованных критериев был бы произвольным.

Проверены предоставленные исходники из папки «Наработки». Перед импортом в удалённом
репозитории находился только README. Код приложения при импорте не переписывался.
Временный файл блокировки Word `docs/~$рспектива дела — проект и ТЗ команде.docx`
и созданный при проверке Python-кеш исключены. Основной DOCX, иллюстрации,
исходники, тесты и прежние протоколы сохранены.

Пять последующих ролей действительно представлены отдельными инструкциями и схемами,
но используют общий простой цикл в app/pipeline.py. Это базовая реализация ролей,
не пять развитых исследовательских агентов с собственными поисковыми инструментами
и стратегиями. IntakeAgent реализован существенно глубже.

## Что проверено заново

- Синтаксис 25 Python-файлов: ошибок не найдено. Проверка через AST также приняла
  синтаксис с feature_version=(3, 10); это не заменяет запуск под Python 3.10.
- Оба JavaScript-файла прошли node --check.
- JSON-файлы разбираются без ошибок.
- Непосредственно выполнен изолированный сценарий SQLite: создание задания,
  повтор с тем же ключом, конфликт другого содержимого, выдача задания,
  контрольная точка, восстановление просроченной аренды, отклонение старого
  владельца, завершение и чтение событий. Сценарий прошёл. Это отдельная
  проверка хранилища, не запуск штатного набора pytest.
- Поиск типичных шаблонов ключей и паролей в текстовых файлах не обнаружил
  кандидатов. .env отсутствует, .env.example содержит пустые значения секретов.
  Такая проверка не гарантирует отсутствие любых чувствительных данных.
- В прежнем reports/ras-gigachat-verified-live.json действительно сохранены
  completed на уровне задания, partial на уровне исследования, три акта
  (18, 10 и 11 страниц), шесть цитат и пустой список предупреждений.
  Все шесть цитат дословно присутствуют на указанных страницах сохранённых текстов.
  Это проверка внутренней согласованности артефакта, не независимое подтверждение
  подлинности актов и не новый сетевой запуск.

## Что не удалось перепроверить

Штатный pytest не запустился: No module named pytest. В доступном Python нет
также FastAPI, Pydantic, HTTPX, psycopg, pypdf и LangChain. Установка из сети
в текущем ограниченном окружении недоступна. Поэтому ни успешный полный запуск
приложения, ни 60 пройденных тестов, ни действующий доступ КАД/RAS/GigaChat
этой проверкой не заявляются. Утверждение «60 passed» есть в прежнем отчёте
reports/delivery-verification-2026-11-08.md. В исходниках найдены 40 функций
test_*; параметризация может давать больше тестовых случаев, так что это
само по себе не противоречие.

PostgreSQL-тестам нужен TEST_DATABASE_URL; без него они пропускаются.
Браузерному тесту нужен Playwright и установленный Edge. Одна команда pytest
в неподготовленном окружении не подтверждает все интеграции. Воспроизводимость
requirements.lock.txt на чистой машине ещё требуется проверить.

## Существенные пробелы и риски

1. **Качество поиска не измерено.** Нет переданного размеченного эталона с
   релевантными/нерелевантными делами, известными контрпримерами и измерениями
   качества. Успешный транспортный вызов не доказывает юридическую применимость.
2. **Отсечение происходит слишком рано.** Pipeline берёт первые три материала;
   локальная библиотека добавляется раньше внешней выдачи. Слабые локальные
   совпадения могут вытеснить более полезные внешние результаты до сравнения.
3. **Локальный поиск примитивен.** Читаются до 1000 последних актов, считается
   наличие первых семи символов слов запроса. Нет embeddings, pgvector,
   полнотекстового индекса и юридических фильтров.
4. **Не исследуется всё дело.** Получение файлов из CaseInstances есть,
   систематического анализа цепочки актов и определения актуального результата нет.
   Сканированные PDF не распознаются. Клиентские документы принимаются как текст/TXT.
5. **Проверена форма цитирования, не смысловая опора каждого вывода.** В Comparison
   и Report нет обязательной связи каждого тезиса с конкретным evidence ID.
   Модель может написать слабое или неподтверждённое объяснение при наличии
   другой корректной цитаты того же дела. Критик не обеспечивает исправление.
6. **Кейс и акт разграничены неполно.** RAS и библиотека отсекают дубли по номеру
   дела, поэтому могут потерять важный отдельный акт. КАД по номеру может вернуть
   несколько актов одного дела. Нужна явная модель «дело → инстанция → акт».
7. **Переносимость запуска не подтверждена.** run.ps1 ожидает доступный python,
   создаёт окружение и ставит lock-файл при первом запуске. PostgreSQL 17,
   локальный сертификат GigaChat и ключи настраиваются отдельно. Без DATABASE_URL
   приложение использует SQLite; PostgreSQL не является обязательным результатом
   простого запуска скрипта.
8. **Документация устарела частями.** README смешивает версии и статусы доступа;
   ссылки на документы до импорта в GitHub были нерабочими. Даже project-status.md
   содержит старое описание 40301 ниже более новой вводной. В HTTP API осталась
   версия 0.1.0. Требуется единое актуальное описание.
9. **Публичная эксплуатация не подготовлена.** Сервер слушает localhost,
   аутентификации и разделения данных пользователей нет. Это ограничение текущего
   формата; перед внешним размещением потребуется отдельная работа.

## Что делать дальше — предложение к обсуждению

1. Воспроизвести установку и демосценарий на чистой машине. Запустить Ruff,
   обычные тесты, PostgreSQL-тесты и браузерный сценарий с явным учётом пропусков.
   Затем отдельно выполнить один разрешённый живой сценарий с настроенными ключами.
2. Привести README к одной текущей версии: цель, готовое, ограничения, запуск,
   проверки, настройка ключей и роли команды.
3. С юристом собрать небольшую проверенную выборку реальных актов и фабул,
   включая нерелевантные дела и противоположные исходы. Сначала измерить качество
   текущего поиска; затем расширять корпус к плановым 300–500 актам.
4. Развить поиск: несколько запросов, пагинация, дедупликация, ранжирование до
   отсечения, индекс. Проверять пользу каждого усложнения на эталоне.
5. Развить исследователя: все значимые страницы, OCR при необходимости,
   цепочки инстанций, раздельные доводы сторон и выводы суда.
6. Ввести связь каждого вывода с доказательствами и цикл исправления замечаний
   критика. Отдельно оценивать качество каждого агента и итоговой выдачи.

Это план обсуждения, а не уже выполненная доработка. На этапе импорта поведение
приложения и старые результаты проверки сохранены без изменений.
